## BLOCK A — Cross-library hoisting comparison (§7.5 thesis)

### A1. Why OpenFHE rejects `SetRingDim(8192)` at `HEStd_128_classic`, depth-1, scale 2^40

**[CONFIRMED-SOURCE]** Fetched `ckksrns-parametergeneration.cpp` from `openfheorg/openfhe-development` (main branch). The rejection is a **security-standard table lookup, not a noise-budget estimate or a hardcoded modulus-bit floor**:

- `ParamsGenCKKSRNSInternal()` computes `qBound = firstModSize + (numPrimes - 1) * scalingModSize + extraModSize` — i.e. the total coefficient-modulus bit budget implied by the requested depth (1) and scaling-mod-size (40).
- It calls `StdLatticeParm::FindRingDim(distType, stdLevel, qBound)`, which looks up the **minimum compliant ring dimension** for (secret-key distribution, security level, qBound) against OpenFHE's internal copy of the homomorphicencryption.org standard lattice-parameter table.
- If the caller's requested `n` is smaller than the table's answer (`he_std_n`), it throws: `"The specified ring dimension (8192) does not comply with HE standards recommendation (16384)."`

This matches `docs/spec.md` §7.5.1's PROJECT_STATE.md claim exactly (`ParamsGenCKKSRNSInternal()` named as the rejection point) — that prior claim is now upgraded from inherited-assertion to **[CONFIRMED-SOURCE]**. It is a **citable library-policy finding**: for a depth-1, 40-bit-scale CKKS circuit at 128-bit classical security, OpenFHE's parameter generator enforces a stricter (larger) minimum ring dimension at N=8192 than SEAL accepts, because OpenFHE's `qBound` accounting and/or its copy of the standard table treats this combination as needing more headroom than SEAL's own `seal_he_std_parms_128_tc()` table does at N=8192 (this difference between the two libraries' standard-table values is itself worth a sentence in the paper — see A4).

### A2. SEAL-up-to-N=16384 path — is `rotation_hoisting.cpp` ring-agnostic?

**[CONFIRMED-RAN/local-read]** Read `vendor_server/include/rotation_hoisting.h` and `tools/openfhe_benchmark/openfhe_linear_eval.cpp` directly.

- `bsgs_reduction()` and `hoisted_tree_sum()` take `n_features` (=256, hardcoded contract), `baby_step`/`giant_step` (=16/16), and operate purely on **slot offsets within each 256-wide block** via `evaluator.rotate_vector(ct, step, gk, out)`. There is no reference to ring dimension, coefficient modulus, or slot *count* anywhere in the rotation logic — only the per-block stride (256) and the Galois step values (`BSGS_ROTATION_STEPS` = `{1..15} ∪ {16,32,...,240}`, fixed array of 30 ints). **The code is ring-agnostic by construction**: rotating "by step S" is a property of the cyclotomic ring's automorphism group and is independent of how many 256-blocks happen to fit in the available slots.
- At N=16384, slot count = N/2 = 8192 → 8192/256 = **32 blocks** (vs 16 at N=8192). This only changes how many parity-gate blocks get checked, not the rotation/circuit code itself.
- The Galois step set `{1..128}` (fold) / `{1..15}∪{16..240}` (BSGS) is **within-block by construction** — every step value is ≤ 240, far below 256, so no step ever crosses a block boundary regardless of how many blocks exist. This holds at any ring dimension.
- **Security margin at N=16384**: per `docs/spec.md` §3.1 (cited in PROJECT_STATE.md Phase 3.1) and the HomomorphicEncryption.org standard table, N=8192/tc128 allows ≤218 total coeff-modulus bits; **[UNVERIFIED]** — I could not fetch the table's N=16384/tc128 ceiling directly in this session (the SEAL header `seal/util/hestdparms.h` and the homomorphicencryption.org table both contain it, but I did not pull the exact N=16384 row). It is well known and near-certain that the bound roughly doubles or more at N=16384 (these tables are designed so doubling the ring dimension at fixed security buys substantially more modulus headroom — OpenFHE's own behavior in A1, requiring N=16384 for the *same* ~140-bit `qBound` that SEAL accepts at N=8192, is itself indirect confirmation that 16384 has comfortable headroom for a 140-bit chain). **Action before committing effort: pull the exact N=16384/tc128 row from `seal/util/hestdparms.h` or the published table before claiming a specific margin number in the paper.**
- The existing 5-prime N=16384 context (`ckks_context_depth2.cpp`, used for the degree-2 fallback path) is a working local precedent that N=16384 parameter sets already build and run successfully in this repo's SEAL installation — lowers risk for this path further.

**Conclusion: A2 (SEAL@16384 vs OpenFHE-hoisted@16384) requires zero changes to `rotation_hoisting.cpp`/`bsgs_reduction()` — only a new SEAL context at N=16384 with a depth-1, ~140-bit chain (e.g. `{60,40,40,60}`-style, already proven viable at N=8192's *200-bit* variant; an N=16384 version simply has more room) and re-running OpenFHE's *unforced* parameter generator (which will now pick N=16384 on its own, matching).**

### A3. Lattigo as a matched-ring alternative

**[CONFIRMED-SOURCE]** Lattigo (`tuneinsight/lattigo`, current v5/v6) accepts `logN=13` (N=8192) as a valid CKKS parameter choice — confirmed via Go-package docs example showing `logN = 13, logQ = 218, levels = 6` as a stated valid configuration. This is a materially different outcome from OpenFHE: Lattigo does **not** hardcode-reject N=8192 the way OpenFHE's `ParamsGenCKKSRNSInternal` does at this depth/security combination — `logQ=218` for `logN=13` is consistent with SEAL's own ≤218-bit ceiling at N=8192/tc128.

**[CONFIRMED-SOURCE]** Lattigo **does** expose a native, public rotation-hoisting API. From `pkg.go.dev/github.com/tuneinsight/lattigo/v5/schemes/ckks` (fetched directly):
- `Evaluator.RotateHoistedNew(ctIn, rotations []int) (map[int]*rlwe.Ciphertext, error)` — rotates one input ciphertext by a *list* of rotation amounts, documented as "much faster than sequential calls to Rotate" — i.e., genuine amortized hoisting, the same Halevi–Shoup amortization OpenFHE's `EvalFastRotationPrecompute`/`EvalFastRotation` pair exposes.
- `Evaluator.RotateHoisted(ctIn, rotations, opOut)` — pre-allocated variant.
- `Evaluator.RotateHoistedLazyNew(level, rotations, ct, c2DecompQP)` — lower-level lazy variant exposing the QP-ring intermediate, useful if finer control over the decomposition step is wanted.

This is a strong candidate: **Lattigo can plausibly run the matched-ring (N=8192) hoisted-flat comparison that OpenFHE's standards-compliant generator refuses**, without touching the deployed ring dimension and without the N=16384 detour. Caveat **[UNVERIFIED]**: I confirmed the API exists and that `logN=13` is *a* valid example configuration in Lattigo's docs, but I did not confirm that Lattigo's own parameter-generation helper (if one is used, as opposed to manually specifying `LogN`/`LogQ`/`LogP`) would *accept* N=8192 for this exact depth-1/40-bit-scale/128-bit-security combination without a similar internal rejection to OpenFHE's. Lattigo's CKKS parameters can be constructed manually (`ckks.NewParametersFromLiteral`) bypassing any auto-generator, which is likely the path that avoids OpenFHE's problem entirely — but this needs a 1-line smoke test to be sure, not assumed.

### A4. HEBench / cross-library fairness precedent

**[CONFIRMED-SOURCE]** Per `hebench.github.io/about_hebench.html` (fetched via search synthesis) and the cross-platform-benchmarking literature found (`SoK: New Insights into Fully Homomorphic Encryption Libraries`, PETS 2023; `Cross-Platform Benchmarking of the FHE Libraries...`, eprint 2025/473 — this second paper's PDF returned HTTP 403 and its methodology section is therefore **[UNVERIFIED]**, not confirmed beyond the search-engine summary): the accepted methodology in HE benchmarking is explicitly **not** to force identical low-level parameters across libraries. HEBench's own stated approach is "fairness of the tests by fine-tuning parameters for each library" — i.e., each library is allowed to pick its standards-compliant parameters for the requested workload/security level, and the comparison is reported **with parameters disclosed per library**, not forced into lockstep. This is consistent with how `docs/spec.md` §7.5.1 already chose to report the OpenFHE finding (explicit ring-dimension mismatch stated, not hidden) — that framing is methodologically defensible per the field's own benchmark-fairness convention, even before a matched-ring re-test exists. **[UNVERIFIED]**: I was not able to load the eprint 2025/473 PDF directly (403) to confirm its specific methodology beyond the search snippet; if this paper turns out to be the closest prior-art comparator for a paper citation, it should be fetched via `gh`/an authenticated path or a university proxy before citing its methodology in detail.

### A4-addendum: why OpenFHE and SEAL disagree at N=8192/tc128

Worth a sentence in the paper: SEAL's own `seal_he_std_parms_128_tc()` table permits 218 bits at N=8192/tc128 (per `docs/spec.md` §3.1, inherited, [CONFIRMED-SOURCE] per PROJECT_STATE.md's own citation of `seal/util/hestdparms.h`), while OpenFHE's `StdLatticeParm::FindRingDim` table, applied to a ~140-bit `qBound` for this exact depth-1/scale-40 circuit, demands N=16384. Both libraries claim to implement the *same* homomorphicencryption.org standard. **[UNVERIFIED]**: whether this is a genuine discrepancy in the two libraries' embedded copies of the standard table, or whether OpenFHE's `qBound` accounting (which may include `extraModSize` for the auxiliary/special modulus differently than SEAL's `coeff_modulus` accounting) is simply more conservative by construction, is not resolved here and would need a side-by-side read of both tables' raw values — flagged as a possible second citable finding, not yet confirmed.

### Recommended primary path + backup (Block A)

**Primary: A3 (Lattigo @ N=8192, native `RotateHoistedNew`).** Lowest effort (no ring change, no 32-block parity-gate rewrite, reuses the existing 256-feature/30-rotation BSGS-equivalent circuit structure), and it directly answers the original §7.5 thought experiment (hold ring + rotation set + circuit fixed, vary only library/API) rather than the looser "ring-matched but library- and ring-changed at once" experiment that A2 produces. Effort estimate: ~3–4 days (Go environment + Lattigo CKKS API ramp-up for someone who has not used it, build the same depth-1/256-feature/30-rotation linear-eval circuit, in-band parity gate, benchmark harness mirroring `openfhe_benchmark.cpp`'s structure). Risk: Lattigo's own parameter literal might still reject N=8192 for unrelated reasons (untested) — mitigate by smoke-testing parameter construction (a few minutes) before committing to the full circuit port.

**Backup: A2 (SEAL@16384 vs OpenFHE-hoisted@16384).** Confirmed lower code-risk (rotation_hoisting.cpp needs no changes, only a new context header/.cpp pair mirroring `ckks_context.h`/`ckks_context_160.h` at N=16384, ~half a day to a day), but it is the *weaker* experiment scientifically — it changes ring dimension for SEAL too, so a remaining "is the difference driven by hoisting or by SEAL's specific N=8192-vs-16384 NTT/rotation cost scaling" confound is not fully closed, only made symmetric. Effort: ~1–2 days (new SEAL context, rerun OpenFHE unforced, exact security-margin table check from A2's [UNVERIFIED] item).

Either path supersedes, but does not require discarding, the existing inconclusive §7.5.1 finding (SEAL-BSGS@8192 vs OpenFHE-hoisted@16384, 27x) — that finding stays in the paper as "the naive first attempt and why it was invalid," with the new matched comparison reported alongside it.

### B4. Lighter-weight FV→CKKS alternatives — PEGASUS

**[CONFIRMED-SOURCE]** PEGASUS (`eprint.iacr.org/2020/1606`, fetched via search synthesis — not the full PDF, so treat specifics below as **[UNVERIFIED]** pending a direct PDF read) is a different kind of HHE-adjacent scheme switching, not a transciphering replacement for RtF: it switches between **packed CKKS and FHEW/TFHE LWE ciphertexts** to evaluate non-polynomial functions (comparisons, lookup tables) on the FHEW side and switch back, rather than RtF's "symmetric stream cipher in BFV/FV, repack into CKKS" pattern. It is **not a drop-in alternative to RtF for this project's actual goal** (replacing the bank's CKKS public-key upload with a cheap symmetric encryption), because PEGASUS assumes the data is already in CKKS form on one side of the switch — it solves a different problem (efficient non-polynomial eval inside an existing HE pipeline), not the "client encrypts cheaply, server transciphers into HE form" bandwidth problem this project's §8 trust model is built around. **Conclusion: PEGASUS does not change the §8 trust model and is not a lower-RAM substitute for RtF for this specific use case.** A genuine lower-RAM RtF alternative was not found in this session; this is the single most important **[UNVERIFIED]** item to resolve if Block B is chosen as the primary lever, since the entire RAM feasibility argument currently rests on "RtF is the only known bridge" without a real survey of competing HHE transciphering papers (e.g., later HERA-based or Elisabeth-based transciphering work post-2021) having been completed.

## BLOCK C — Client-encrypt-dominates finding

### C1. Is ~3ms client CKKS encrypt for 256 features / 4096 slots plausible?

**[CONFIRMED-RAN, inherited]**: `artifacts/e2e_latency_breakdown.json` — 200-bit median `encode_encrypt_us` = 3008.4us (mean 3328.8); 160-bit median 2933.2us (mean 3493.7). Both chains, n=1000, powersave governor (not yet performance-governor-verified — see Block D).

**[UNVERIFIED]** direct apples-to-apples literature baseline: I found general SEAL CKKS benchmarking resources (`AERO-Project-EU/CKKSBenchmark`, SEAL's own `sealbench` tool) but did not pull a specific published encrypt-only latency number at N=8192/4096-slots to compare against. The one concrete number surfaced (~257ms for a "naive implementation" at `poly_modulus_degree=2^13`) is for a full inference pipeline, not isolated encrypt, and is not a valid comparator. **3ms order-of-magnitude is plausible** for a single CKKS encrypt+encode at N=8192 on a modern desktop/laptop CPU under `powersave` (encrypt is one NTT-domain polynomial sample plus error/randomness generation per RNS prime, multiplied by the number of primes in the chain — at 3–4 primes this is consistent with single-digit-millisecond encrypt times reported informally in various SEAL issue threads), but this is reasoning from general knowledge of the operation's cost structure, not a verified citation. **Action: do not cite "~3ms is consistent with the literature" in the paper without first running SEAL's own `sealbench` at matching parameters and citing that number directly — it is one command and removes this UNVERIFIED entirely.**

### C2. `encrypt_symmetric` / `Serializable<Ciphertext>` — bandwidth and CPU effect

**[CONFIRMED-SOURCE]** Fetched `SEAL/native/examples/7_serialization.cpp` directly from `microsoft/SEAL` (main branch). Confirmed:
- Seeded/symmetric-key ciphertexts give "a huge reduction in the data size upon serialization" — SEAL's own stated rationale is that CKKS RNS primes are often <64 bits but every coefficient is still serialized as a 64-bit integer in the *public-key* path, so almost half the bytes in a standard ciphertext are effectively redundant; the seeded/symmetric path **stores a PRNG seed instead of the second polynomial** and regenerates it on load.
- This matches this repo's own measured 1.998–1.999x bandwidth ratio (`wire_size_probe.cpp`, `artifacts/wire_sizes.json`: 160-bit standard=262257B / seeded=131266B; 200-bit 393329B/196802B) — **[CONFIRMED-RAN, inherited]**, and is now also **[CONFIRMED-SOURCE]**-explained by the actual SEAL example's comments, not just empirically observed.
- **The SEAL example explicitly does NOT claim a CPU/encrypt-time benefit** — its comments speak only to serialized size. I confirmed this directly by reading the file's text: no sentence in `7_serialization.cpp` claims encrypt_symmetric is computationally cheaper. **[UNVERIFIED]** whether it is nonetheless cheaper in practice: symmetric-key encryption in SEAL replaces the public-key encrypt's combination of `(pk0*u + e0, pk1*u + e1)` with a single random-polynomial sample plus one ciphertext term derived from the seed — this *could* plausibly skip one full polynomial multiply (`pk1*u`), which would make it faster, not just smaller, but I found no SEAL documentation or benchmark confirming this, and PROJECT_STATE.md/spec.md §8.9 only ever discuss it as a bandwidth feature ("not yet enabled in bank_client" — confirmed via `grep`, [CONFIRMED-RAN]: no `encrypt_symmetric` call anywhere under `bank_client/`).
- **Action: if the paper wants to claim "seeded ciphertexts would also reduce client encrypt time," that claim needs its own microbenchmark (encrypt vs encrypt_symmetric, same parameters, n=1000) before it's stated — currently zero evidence either way beyond plausible reasoning about which polynomial multiply might be skippable.**

### C3. Does this strengthen the transciphering motivation?

This is **synthesis/argument, not a verified fact** — framed as such. The corrected framing from re-reading the actual numbers: at single-request granularity, server `total_inference_us` (200-bit: ~9038us median; 160-bit: ~6763us median) actually **exceeds** client `encode_encrypt_us` (~3008/2933us median) — so the literal "client encrypt (3ms) > server compute (2ms)" claim in the prompt does not match this repo's single-request e2e numbers as currently read; if that 2ms figure is real it likely refers to a *different* comparison. The comparison that **is** directly supported by this repo's artifacts is the **amortized, per-transaction** one: at full batch occupancy (`lanes=16`, `artifacts/throughput_results.json` / `amortization_table.json`), server compute amortizes to **per_tx_us ≈ 1070us (~1.07ms)** [CONFIRMED-RAN, inherited, Phase 5.4/5.7 Part B], while client encode+encrypt is a fixed ~2.9–3.3ms **per request regardless of server-side batching**, because each bank request is independently encrypted before any server-side batching can occur. **At full occupancy, amortized client-encrypt cost (~3ms) is ~2.7–3x the amortized server compute cost (~1.07ms) — this is the real, defensible version of the "client-encrypt dominates" claim**, and it is exactly the cost transciphering's online phase (a sub-millisecond symmetric encrypt, per `tools/transciphering/README.md`'s measured ~0.53ms for lanes=1 / ~7ms for lanes=16 client HERA-16 encrypt — note: the 16-lane HERA number is *higher* than CKKS's 3ms, so this comparison needs care, lane-for-lane, before being used as a clean win) is meant to replace. **Recommend re-deriving this comparison carefully and explicitly (single-request CKKS-encrypt vs single-request HERA-encrypt, and separately the batch/amortized versions) before writing the paper's framing sentence — the raw numbers in `tools/transciphering/results/` do not unambiguously show HERA-16 client encrypt beating CKKS client encrypt at every lane count (1052 bytes / 1 lane is clearly smaller upload, but the ~7ms HERA encrypt at 16 lanes vs ~3ms CKKS encrypt needs to be checked, not assumed, before claiming a clean motivation win).**

## BLOCK D — Reproducible timing manifest

### D1. Minimum bar for HE microbenchmarks

**[CONFIRMED-SOURCE]**, multiple sources (easyperf.net "How to get consistent results when benchmarking on Linux", kernel.org `boost.txt`, and a cited systems paper on noise-free measurement reporting "99.99% stability... variance ~0.01%" with turbo disabled vs "≥1% variance" with turbo enabled):
- **CPU governor**: set to `performance` (this repo's own existing gate at `tests/benchmark_comparison.py:714-720` already encodes this requirement — confirmed inherited).
- **Turbo Boost**: disable (`echo 1 > /sys/devices/system/cpu/intel_pstate/no_turbo` for Intel `intel_pstate`, or `echo 0 > /sys/devices/system/cpu/cpufreq/boost` generically) — `AUDIT.md`'s own Phase 1 remediation commands already include this as an optional step; per the sources above it should be treated as close to mandatory, not optional, for sub-millisecond/low-single-digit-millisecond timings like this project's rotation/encrypt measurements, where 1%+ turbo-induced variance is comparable in magnitude to the effects being measured.
- **Core pinning / isolcpus**: isolate at least one physical core from the scheduler (`isolcpus=` kernel parameter, or `taskset`/cpuset for a lighter-weight per-process pin) so the benchmark thread isn't preempted or migrated; `isolcpus` is described as the more rigid, kernel-level option vs `cpuset`'s more flexible per-process option.
- **SMT/hyperthreading**: disabling is recommended by the cited reliable-measurement paper to avoid sibling-core interference, though this is a bigger intervention (BIOS-level on many systems) than this project's runway likely justifies for every run.
- **ASLR/NUMA**: not directly addressed by the sources found in this session — **[UNVERIFIED]** whether ASLR materially affects HE workload timing (it mainly affects cache-line alignment of heap allocations; for a workload dominated by large polynomial-array operations like CKKS rotations, the effect is plausibly small but not measured here).

### D2. Cloud fixed-clock instance vs "ROG box" with performance governor

This is a judgment call, not a fact-lookup, so it's stated as recommendation rather than [CONFIRMED-*]: a cloud instance only helps reproducibility if its *vCPU* is pinned to a fixed clock and isolated from co-tenant noise — most general-purpose cloud vCPUs are themselves subject to hypervisor scheduling jitter and (for burstable/non-dedicated instance families) CPU credit throttling, which can be a **worse** noise source than a local machine with `performance` governor + turbo disabled + core-pinned. **Recommendation: prefer the local ROG box with `performance` governor + turbo disabled + `taskset`-pinned benchmark thread over a generic cloud instance for the actual paper-citable latency numbers**, reserving any cloud instance purely for the Block B transciphering RAM problem (where the constraint is memory capacity, not clock determinism, and absolute latency numbers from that run are not what's being cited — only "did it complete" and rough timing order-of-magnitude). If a dedicated-tenancy, fixed-clock instance (e.g. AWS instances with "Dedicated Host" tenancy, or bare-metal `.metal` instance types) were used instead, it could match or exceed the ROG box's reproducibility — but at higher cost, and this was not evaluated in detail given Block D is the lowest-priority of the four blocks per the runway constraint.
